# قياس الكاتب ثم أثره في مسار محاور كاملًا

## حدود الاستنتاج

الاختبار الأول هو `compare_writer_plans.py`: سؤال ومقاطع ومطالب ثابتة، مع تغيير الكاتب فقط. الثاني هو `compare_full_pipeline.py`: فهم وبحث وكتابة وفحص وإعادة كتابة وإخراج JSON عبر `/api/ask` داخل عملية معزولة باستخدام TestClient. يختبر الثاني أثر **الكاتب التجريبي داخل نفس بناء الشيفرة**؛ ليس مقارنة كل تغييرات الفرع بخادم الإنتاج القديم. لا تعديل للخدمة أو إعداداتها أو ذاكرة أجوبتها. لا يقيس شبكة الزائر أو المتصفح أو التحمل المستمر. قياس هذه الطبقات أو مقارنة إصدارين كاملين يحتاج تجربة منفصلة.

الأسئلة والنتائج المحفوظة السابقة كلها تطويرية ومكشوفة. لا يوجد الآن ملف مستقل بحكم مرجعي بشري معتمد. لا نحوله آليًا إلى holdout، ولا نملأ الأحكام الدلالية باختبارات الشيفرة أو بنموذج الكاتب نفسه. التحقق من إعلان الاستقلالية وهوية المراجع وتمثيل الأسئلة مسؤولية بشرية؛ الشيفرة لا تستطيع إثباتها.

## 1. الكاتب: شرط الانتقال

تشغل مقارنة الكاتب الصغيرة وفق `EVIDENCE_PLANNING.md`، ثم تحلل ملفها بلا شبكة. ملف المراجعة المنفصل يحوي معرفات A/B، بصمة الرد، أحكامًا فارغة واسم المراجع. يراجع المختص صحة المعنى والشروط والنسبة ودرجة الحديث وتغطية المطلوب والتكرار، مستعينًا بالمقاطع الكاملة.

قبل تنفيذ holdout للمسار الكامل، يلزم `--writer-results` و`--writer-labels`: يجب اكتمال جميع أزواج الكاتب ومحاسبة تكلفتها، وتطابق بصمات الردود والشيفرة، واكتمال الأحكام البشرية على المسارين، ونجاح ردود المرشح في السند والتغطية دون تكرار غير لازم. لا يشترط أن يكون الكاتب الحالي مثاليًا؛ قد يكون تحسينه غاية التجربة. النتائج القديمة قابلة للتحليل دون إعادة مدفوعة، لكن تغيير شيفرة الكاتب يبطل استعمال التجربة القديمة لاعتماد الكاتب الجديد.

## 2. ملف أسئلة المسار الكامل

`evaluation/paired-protocol/development.example.json` مثالان قديمان للتشخيص، بأحكام مقترحة معلقة؛ لا يثبتان تحسنًا عامًا. فحصهما بلا شبكة:

```bash
python scripts/compare_full_pipeline.py evaluation/paired-protocol/development.example.json
```

كل حالة تحدد `id/question/style/lang` ومرجعًا سابقًا للتشغيل: السلوك المتوقع، المطالب، وأدلة بمعرفات المقاطع و`text_sha256` للنص الكامل و`passage_sha256` لجميع حقول المقطع، ومنها المصدر والموقع والدرجة والترجمة. يتحقق التنفيذ من وجود المقطع وتطابق نصه قبل إرسال أسئلة مدفوعة. تبقى النصوص ودرجة الحديث ونسبة القول هي المرجع، لا مجرد ظهور رقم مصدر في الجواب.

العينة المستقلة تستخدم `partition=declared_holdout` و`cluster_id` مستقلًا لكل عائلة أسئلة؛ لا تعد الصياغات المتقاربة أو الترجمات أو إعادة السؤال عينات مستقلة. تتطلب المراجع `review_status=approved` واسم المراجع، وأدلة للأسئلة المتوقعة الإجابة. يحفظ `independence` إعلانًا من مراجع خارجي بـ`not_used_in_development=true` و`reviewer` وبصمة قائمة أسئلة التطوير `development_questions_sha256`. لا يسمح بسؤال تجربة الكاتب نفسه داخل holdout. هذا تدقيق لإعلان ومراجع مقدمة، لا شهادة آلية بأنها لم تُكشف سابقًا.

يختار المراجع الأسئلة قبل رؤية النتائج من المجالات والأساليب واللغات المستهدفة: نص الحديث ودرجته، الشروط والنفي، نسبة الأقوال والخلاف، سؤال متعدد المطالب، عدم كفاية الأدلة، الإحالة والرفض الصحيحان. الاستقلالية وتمثيل استخدام محاور أهم من مجرد تكثير العدد. هذا الإصدار يقيس أسئلة منفردة؛ الحوار المتتابع والتحمل لهما مجموعتان منفصلتان لاحقًا.

## 3. شروط القياس والدفع

التنفيذ يكون في عملية جديدة، ببيئة المزود وقاعدة المصادر والفهرس المحلي المثبتة، ثم:

```bash
python scripts/compare_full_pipeline.py MANIFEST.json --execute \
  --manifest-sha256 EXACT_MANIFEST_HASH \
  --writer-results WRITER_RESULTS.jsonl --writer-labels WRITER_REVIEW.json \
  --max-model-http-attempts 150 --stop-after-usd 0.10
```

الأرقام مثال لحدود تجربة تطوير محدودة، وليست ميزانية أو حجم عينة كافيين للـholdout. لا تنفذ المثال قبل اختيار حدود مناسبة لملفك. `--execute` منفصل عن الفحص المحلي، ولا تُطلب مفاتيح أو تُطبع في السجل. لا توجد هنا جلسة SSH أو مفاتيح مزود، لذلك لم تنفذ تجربة نموذج حقيقية أثناء البناء.

- العدد المعلن للأسئلة هو مرتان لكل حالة، وليس عدد استدعاءات النموذج. يحفظ كل طلب بدأ قبل تنفيذه، ويبدل الترتيب current/candidate ثم candidate/current بين الحالات. لا يعاد سؤال فاشل تلقائيًا. تبقى retries/fallback الخاصة بالمسار نفسه محسوبة ومقيدة بميزانية النقل.
- حد `max-model-http-attempts` يطبق تحت قفل قبل كل اتصال مزود فعلي حتى مع فحص متوازٍ. تحفظ الطلبات وردود المزود الناجحة في ملف خاص لتفسير فشل الفاحص لاحقًا، دون URLs أو headers أو مفاتيح. التكلفة المجهولة توقف بدء اتصالات إضافية؛ المهلة ليست مجانية. قد تنتهي اتصالات متوازية بدأت مسبقًا. يبقى حاجز النقل مغلقًا في عملية التقييم عند الانتهاء، حتى لا تبدأ أعمال خلفية متأخرة اتصالات جديدة بعد إزالة الحارس؛ ما لم يصل رده يبقى ذا كلفة مجهولة. عتبة الدولار توقف بعد الرد وليست سقف إنفاق مضمونًا.
- الأجوبة المحفوظة على القرص والذاكرة معطلة في العملية المعزولة. لكل مسار ذاكرة تضمين استعلامات منفصلة؛ يشتركان في المقاطع والأوزان المحلية المثبتة فقط. يسخّن النموذج المحلي خارج التوقيت، ولا يسمح بتضمين بعيد ذي كلفة غير محاسبة. ظروف OS cache والمزود تبقى قيودًا معلنة.
- الطلبات متسلسلة، مع حصة زائر تجريبية معزولة تكفي للعينة؛ ليست تجربة حدود الزيارات أو التزامن. يبدأ الزمن عند إرسال TestClient وينتهي بعد JSON الكامل. يشمل تسجيل القياس الخاص، ويستبعد بدء العملية وتحميل النموذج وبصمات الملفات وشبكة الزائر والمتصفح. لا تطرح مجموع مراحل متداخلة من الزمن الكلي.
- تفصل التتبعات حسب request_id وتنتظر اكتمال العمل الخلفي. تحفظ مصادر الجواب كاملة ومعرفاتها، والمزود الفعلي وأسباب التوقف داخل التتبع، وأزمنة ونتائج كل سؤال، بما فيها التعذر. تراجع قاعدة المصادر والفهرس قبل التجربة وبعدها. أي نقص أو تغير يغلق بوابة الاستنتاج.
- يوجد حاجز ملف يمنع إعادة الخطة نفسها على الشيفرة نفسها في مجلد التجربة. عند التوقف حلل النتائج المحفوظة أولًا؛ لا تعاود دفعة مدفوعة لمجرد أنها لم تكتمل.

## 4. المراجعة والنجاح

```bash
python scripts/compare_full_pipeline.py FULL_RESULTS.jsonl --analyze
python scripts/compare_full_pipeline.py FULL_RESULTS.jsonl --analyze --labels FILLED_REVIEW.json
```

يولد التحليل ملف مراجعة معمى منفصلًا A/B لا يعرض الوضع أو الزمن أو الكلفة، ويحتوي السؤال والمرجع والجواب ومصادره وبصمة الرد. تبقى حقول المعنى، الشروط، النسبة والدرجة، التغطية، صحة سلوك الإجابة/الامتناع/الإحالة، والخطأ الحرج فارغة. يملؤها مراجع مستقل باسمه. الخطأ الحرج يشمل اختلاق نص/مصدر أو تحريف درجة رواية أو إسقاط قيد يغير الحكم؛ لا يعد عدم التعذر دليل صحة تلقائيًا. اختلاف تقييم المراجعين يحتاج تحكيمًا قبل استعماله كحكم نهائي.

يتحقق التحليل من تطابق الأحكام مع بصمة الجواب، ويمنع تكرار النتائج، ويطابق تكلفة اتصالات النموذج مع تتبعات كل سؤال ومجموعها. لا تختفي الأسئلة الفاشلة ولا التكاليف المجهولة من المقام. ويعرض التقرير حالات القبول غير المسند والقبول الخاطئ والرفض الخاطئ ونقص التغطية والأخطاء الحرجة لكل مسار، من الأحكام البشرية؛ المقام أسئلة مستقلة لا عدد جمل أو محاولات. تبقى معرفات المسارين في تقرير منفصل عن ملف المراجعة.

تُكتب الحدود مسبقًا في `success`؛ المثال يستعمل:

1. صفر أخطاء حرجة مرصودة للمرشح، والحد الأعلى أحادي الجانب لمعدلها لا يزيد عن 1%.
2. الحد الأعلى للحالات التي نجح فيها الحالي وفشل المرشح لا يزيد عن 1%. هذه مقارنة محافظة لعدم التراجع لا تعوض الضرر بفوائد في أسئلة أخرى.
3. اختيار مقياس رئيسي واحد قبل القياس: cost أو latency. الحد الأعلى لنسبة متوسط المرشح إلى متوسط الحالي يجب أن يكون أقل من 1؛ لا نختار المقياس الأفضل بعد رؤية النتائج. يشمل الحساب كل الحالات المكتملة بمراجعتها وسلوكها المتوقع، وليس الإجابات المقبولة وحدها.

تحسب حدود الأخطاء بطريقة Clopper–Pearson أحادية الجانب، وحد الأداء بـpaired percentile bootstrap على الأسئلة المستقلة (4000 سحب ببذرة ثابتة). مع صفر أخطاء وalpha=0.05، العشرة تعطي حدًا أعلى نحو 25.9%، والمئة نحو 2.95%، و299 نحو 0.997%؛ صفر أخطاء في عينة صغيرة لا يثبت موثوقية عامة. المعيار لا يساوي عددًا سحريًا: التجميع الدلالي وتمثيل الأسئلة وجودة المرجع لازمة، وقد يتطلب الأداء/التراجع عددًا أكبر. فواصل الأداء تقريبية، وثقة كل معيار منفردة وليست ضمان ثقة مشتركة لكل المعايير؛ التعميم العلمي النهائي يحتاج مراجعة التصميم الإحصائي.

لا تكون `general_improvement=true` إلا لعينة holdout معلنة، ومراجعة الكاتب ناجحة، وتنفيذ كامل على مصادر وشيفرة ثابتة، ومحاسبة متطابقة، وأحكام بشرية كاملة، وتطابق مسارات المزود المبلغ عنها، واجتياز حدود الجودة والمقياس الرئيسي. هذه بوابة مشروطة بصحة إعلان الاستقلالية والمرجع والافتراضات، وليست تصديقًا شرعيًا أو اعتماد نشر تلقائيًا. فشل البوابة يظل فشلًا حتى لو كان الرد أسرع.
